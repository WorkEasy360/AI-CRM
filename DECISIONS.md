# DECISIONS

Assumptions made while building the Bigin-equivalent specification on the existing WorkEasy CRM codebase.
Earlier architecture decisions stay in `docs/adr/` (ADR-0001 … ADR-0013); this file records what the
spec asked for, what was decided instead or in addition, and why. Newest milestone last.

## Global

| # | Decision | Why |
|---|---|---|
| G1 | **Keep the existing stack** (Django 5.2 + DRF, PostgreSQL 16 RLS, Celery + Redis, Next.js 15 + React + TypeScript, Tailwind) instead of the spec's NestJS/Prisma/Vite/BullMQ. | The product already runs in production on this stack with about 1,000 passing backend tests, RLS tenant isolation and an AWS deployment. A rewrite would throw away proven security work for no user-visible gain. The repo's `CLAUDE.md` mandates this stack. The spec's *mandates* (tenant guard + RLS, event bus, entitlement service, provider adapters, async queues, API-first + OpenAPI) are met with these equivalents: DRF + drf-spectacular (OpenAPI 3), Celery queues (DLQ via retries + sweeper tasks), `apps.core.domain_events`. |
| G2 | **Evaluate before building.** Where a feature already exists it is kept and aligned to the spec; only gaps are built. | Per the product owner's note. |
| G3 | **Branding:** the product stays **WorkEasy CRM** (navy `#1B3040` chrome, brand green `#4ADE80`). The top edition is named **"360"** in the UI and `edition_360` in code, not "Bigin 360". | "Bigin" is a Zoho trademark. The limits and prices match the spec exactly. |
| G4 | **Search:** PostgreSQL full-text + trigram (ADR-0011), not OpenSearch, until a tenant's data shows it is needed. | Same results at this scale with one fewer stateful service to run and secure. |
| G5 | **Infra:** AWS (ap-south-1) with Docker Compose for dev. Kubernetes/Helm is not adopted (ADR-0008). | The current one-instance deployment meets the budget. Helm charts can be added when horizontal scale is actually needed. |

## Milestone 1: Foundation

| # | Decision | Why |
|---|---|---|
| M1.1 | **EntitlementService = `apps/billing/entitlements.py`.** Editions are code-defined in `apps/billing/editions.py`, never in the DB. | Like system roles: a limit is a reviewed change, and the database cannot drift from the pricing page. |
| M1.2 | **Counters:** records, AI credits and mass emails use `UsageCounter` rows moved by one conditional `UPDATE … WHERE used + n <= limit` (atomic, no lost updates, cannot overdraw). Low-volume totals (pipelines, custom fields, seats) are counted live under a `SELECT … FOR UPDATE` on the subscription row. Not Redis. | Postgres gives exact, transactional enforcement: a failed create rolls its consumption back with it. A Redis counter would need two-phase compensation. `billing.reconcile_usage` (every 6 h) re-derives totals from the owning modules, so drift through paths that skip the service layer (erasure, purges, the load-test seeder) self-heals. |
| M1.3 | **Layering:** billing never reads other modules' tables. Each module registers how to count its own rows via `entitlements.register_counter` from its `AppConfig.ready()`. | Spec: "No module reads another module's tables directly." This mirrors `domain_events`. |
| M1.4 | **What counts as a record:** non-archived contacts + companies + deals + products. Archiving (recycle bin) frees the slot; restoring takes it again. | Bigin counts records across modules. A trashed record should not block new work. |
| M1.5 | **Trial:** new organizations start on a **15-day Premier trial**. When it lapses (or a cancelled plan's period ends) the org resolves to **Free** at read time; no job is needed. Data above Free limits is kept and new creates are blocked. | Matches Bigin's onboarding. Resolving lazily means a missed cron can never leave a lapsed trial on Premier. |
| M1.6 | **Existing organizations are grandfathered** onto `edition_360` (active, no seat limit) by migration `billing/0002`. | Introducing editions must not take capabilities away from live tenants. |
| M1.7 | **Production safety switches:** `BILLING_ENABLED` (prod default **off**: new orgs are grandfathered as before) and `BILLING_SELF_SERVICE` (prod default **off**: plan changes and add-ons answer 409 "contact support"). Both default on in dev and test. | No PaymentProvider is wired yet (Milestone 11). Self-service upgrades without payment would let anyone give themselves 360 for free. |
| M1.8 | **Seats:** Free = 1 user. On a paid, active edition the seat limit is the purchased licences (`seats`). Trials and grandfathered orgs are not seat-limited. `organization.settings.max_users` still overrides (enterprise contracts). Pending invitations take a seat. | The spec says "unlimited users" with "per-seat add and remove". In Bigin, licences cap users. |
| M1.9 | **Mass-email daily caps** for Express/Premier are not given in the spec. Assumed **250/day (Express)** and **500/day (Premier)**; 360 = 1,000/day as specified. | Needed for "daily volume caps by edition". |
| M1.10 | **Add-ons** (catalogue in `editions.py`): records 5,000, automations 10, pipelines 1, booking pages 1, mass email 500/day, AI credits 1,000 (one-off, current month only), File Cabinet 5 GB, scheduled backup (feature). Prices are placeholders. Add-ons need a paid edition and raise limits immediately (resolved on every check). | The spec lists the add-on kinds but not their sizes or prices. |
| M1.11 | **Upgrade prompt contract:** a blocked action answers **403** with problem type `plan_limit_reached` / `feature_not_in_plan` / `user_limit_reached` and an `upgrade` member `{kind, metric|feature, limit, used, current_edition, required_edition, addon, url}`. | One shape the web and mobile clients render inline at the boundary. |
| M1.12 | **Gates enforced now:** records (create/restore/bulk restore, imports), pipelines, custom fields per module (create/restore), seats, email integration (connect + send), WhatsApp (connect + send), AI suite (copilot 403; Ask Keel degrades to a CRM-only answer with a "plan" notice). Gates for modules that don't exist yet (automation rules, booking pages, Email-In, File Cabinet, stage transition rules, …) are added in the milestone that builds each module, calling the same service. | Every gated action passes through the one service. |
| M1.13 | **AI credits:** the counter and allowance (Premier 1,000 / 360 3,000 / month) exist now. Debiting per AI action moves into Milestone 8 together with the credit ledger UI. | Each AI feature has to declare its credit cost, and that belongs with the AI work. |
| M1.14 | **Roles vs profiles:** the existing `authz.Role` is Bigin's **Profile** (a permission set with record scopes). The new `authz.HierarchyRole` is Bigin's **Role** (a self-referencing reporting tree). Each member has one of each (`Membership.role`, `Membership.hierarchy_role`). | Keeps every existing permission check unchanged. The hierarchy only adds what "role and subordinates" needs. |
| M1.15 | **New scope `subordinates`:** the actor's own records plus those owned by members in roles strictly below theirs. If the role has `share_with_peers`, members of the same role are included. Members with no hierarchy role see only their own records under this scope. `subordinates` and `team` reach different people, so neither implies the other; only `all` covers both. | Matches Bigin's visibility model. It fails closed. |
| M1.16 | **Deleting a hierarchy role** moves its sub-roles and members up to its parent. Cycles are refused. | Nobody falls out of the tree and nobody silently loses visibility. |
| M1.17 | **Custom permission sets** (`/api/v1/roles/`): they can never hold owner-only permissions (`org.delete`, `org.billing`, `privacy.delete_data`). Nobody may create, edit or assign a set granting more than they hold. A set still in use cannot be deleted. System roles are read-only. | Prevents privilege escalation through role management. |
| M1.18 | **Field-level permissions** (`/api/v1/roles/{key}/field-permissions/`): per permission set and module, a field is `hidden` or `read_only` (default read/write). Enforced in the CRM read serializers (list, detail, Kanban card, stage totals when `amount` is hidden), in exports, and on every create/update in `apps.crm.records` (403 `field_read_only`). Values derived from a restricted field (deal `amount_base`, `weighted_amount_base`) inherit its rule. The Owner set and identity fields (`id`, `name`, `owner`, `version`, timestamps, `tags`) cannot be restricted. | Spec G: field-level read/write masking. |
| M1.19 | **Known gap (closed in Milestones 7 and 8):** aggregates in dashboards/forecast and AI/RAG answers do not yet apply field masking. | Those surfaces are rebuilt in the Analytics and AI milestones, and masking is part of their acceptance. Until then, don't restrict fields for roles that need AI or dashboards to be leak-free. |
| M1.20 | **Audit:** every billing, permission-set, hierarchy and field-rule change writes an audit event with `before`/`after`. The existing append-only audit log (DB trigger) is kept. The user agent is stored as a hash. | Privacy by default (DPDP/GDPR). The hash still correlates sessions for investigations. |
| M1.21 | **Auth:** the existing allauth stack (password, TOTP, WebAuthn/passkeys, recovery codes, org-enforced MFA, Workeasy360 OIDC SSO) satisfies the foundation. SAML 2.0, social sign-in (Google/Microsoft/LinkedIn/X/Facebook), IP allowlisting and push MFA are Milestone 11. | Avoids building identity twice. |

## Milestone 2: Core CRM

| # | Decision | Why |
|---|---|---|
| M2.1 | **What counts as a record (confirmed, M1.4):** active (not in the recycle bin) contacts, companies, deals and products. Activities, notes, files, tags, price books and saved views do not count. Every create, restore, import and import rollback moves the one counter through `entitlements.consume/release`. Settings → Plan & usage now shows the per-module breakdown and this definition (`record_definition` in `/billing/usage/`). | Customers will dispute the number; the page shows how it is made up, from the same counters that enforce it. |
| M2.2 | **Module schema registry (`apps.crm.schema`).** Each module registers its fields as data from `AppConfig.ready()`; custom fields are appended at read time; `fields_for(actor)` drops hidden fields and flags read-only ones. Sheet view, saved-view columns, the generic Kanban/Calendar/Chart, import targets, export columns, pipeline layouts and the field-permission editor read it. The existing per-module read serializers keep their explicit field lists: they are the published API contract. | M3 adds custom fields and custom modules by registering more of the same, with no rework of the consumers. |
| M2.3 | **Per-pipeline access.** A top-level pipeline can be `restricted` to teams and/or hierarchy roles (`PipelineAccess`). Members outside the grants do not see the pipeline, its stages or its deals anywhere; pipeline managers (`pipelines.manage`) always see every pipeline. Enforced by a new visibility-rule registry in `authz.service` that `scope()` and `check()` apply, so every list, detail, board, search, export, aggregate and background job already honours it. An activity linked to a hidden deal shows no deal reference. | One enforcement point; a new read path cannot forget it. Managers cannot lock themselves out. |
| M2.4 | **Sub-pipelines** are one level deep (`Pipeline.parent`), have their own stages, share the parent's layout and access, cannot be the default, are capped at 10 per pipeline, and **do not count against the edition's pipeline limit**. | The spec calls them variants of a team pipeline; Bigin limits team pipelines, not their variants. |
| M2.5 | **Pipeline templates are our own wording** (Sales, Inbound enquiries, Services engagements, Renewals, Partnerships). New organizations start with "Sales pipeline": Discovery → Fit confirmed → Proposal sent → Terms agreed → Won / Lost (same probabilities as before). Existing pipelines and stages are untouched. | The old default overlapped other CRMs' default stage names. |
| M2.6 | **Line items and the deal amount.** A line stores subtotal (quantity × price less discount), tax (charged on the subtotal) and total. While a deal has lines its amount is the **sum of line totals, tax included** (`amount_from_lines`); a manual amount is refused (409 `amount_from_lines`) and the currency cannot change. Removing the last line unlocks the amount and keeps its last value. Deals that had lines before M2 keep their manual amount until one of their lines changes (migration `deals/0009` only splits stored line totals into subtotal + tax). Every line change bumps the deal version, announces the deal and is audited. | Matches a quote's grand total; never rewrites a live tenant's deal values silently. |
| M2.7 | **Price books** are single-currency organization configuration (not records, no record-limit cost). Reading needs `products.view`; changing needs the new `pricebooks.manage` (Owner, Admin, Sales Manager). A deal may name an active book in its own currency; new lines take the book's price, else the list price. A book price is hidden wherever the product's `unit_price` is hidden. | Pricing authority stays with managers; a hidden price must not leak through a price list. |
| M2.8 | **Stock flag** = `Product.in_stock` (boolean, default true). No quantities or inventory movements. | The spec asks for a flag; inventory is out of scope. |
| M2.9 | **Line-item field permissions** use a new field-rule module `deal_line` (quantity, unit_price, discount_percent, tax_rate; subtotal, tax and total derive from unit_price). Because lines set the deal amount, a read-only or hidden deal `amount` makes lines read-only and hides their money. | The amount cannot be protected while its inputs stay writable. |
| M2.10 | **"Event" is the existing `meeting` activity kind.** The API value stays `meeting`; new UI text says Event. | Renaming the stored kind would break live data and integrations. |
| M2.11 | Notes and files now attach to activities too. **Tags do not** attach to activities in M2. | Tags drive list filters activities do not have yet; M3's dynamic field layer is the natural place. |
| M2.12 | **Recurrence:** an RRULE subset (DAILY/WEEKLY/MONTHLY/YEARLY with INTERVAL, COUNT ≤ 1000 or UNTIL, BYDAY …; no sub-daily, no DTSTART/RDATE/EXRULE). Events are stored once and expanded into occurrences when read (calendar, My day). Tasks roll forward: completing one creates the next occurrence. Calls do not repeat. Occurrences are not edited one by one (no per-occurrence exceptions in M2). | Bounded, safe expansion; exceptions arrive with calendar sync (M4). |
| M2.13 | **Subtasks:** tasks under a task, one level, at most 50; they inherit the parent's record links and appear in task lists as well as under their parent. | A subtask assigned to someone else must still reach their task list. |
| M2.14 | **Bulk activity actions** (reassign, complete) need the new `activities.bulk_update` (Sales Manager and above); reassigning also needs `activities.update` at scope "all". All ids must be in scope or nothing changes. One audit event lists every id; every activity gets its own domain event and version bump. | Same contract as the record bulk actions. |
| M2.15 | **Search stays on PostgreSQL full text (G4).** It now honours field permissions: summaries never show a hidden field, and when a searchable field is hidden from the member, matching falls back to their visible columns. List filters and sorts on a hidden field are refused exactly like unknown ones (400). | Otherwise "search by phone" or `?amount_min=` would reveal hidden values. |
| M2.16 | **Saved views** (`/views/`): kinds list, kanban, sheet, calendar, chart; visibility private / organization / teams; sharing needs the new `views.share` (Sales Manager and above); only the owner edits or deletes; one default per member and module. Opening a view never widens access: it runs with the viewer's scope and field rules, and columns or filters on fields the viewer cannot see are dropped (`restricted: true`). | Views are presentation, not permission. |
| M2.17 | **Sheet view:** rows are read in offset windows (≤ 500) with a two-step fetch (ids, then full rows) and a count capped at `SHEET_COUNT_CAP` (1,000,000). Edits go row by row through the module's own update (field rules, versions, events, one audit event per record, audit rows inserted together). Hidden and unknown fields both answer `field_not_editable` (no oracle); read-only answers `field_read_only`; each cell is validated alone so good cells save; a version conflict writes nothing of that row and returns the current values; a deal stage cell is a stage move. Lookups, owner and pipeline are edited on the record page in M2. Editing needs `<module>.update` per row, not `bulk_update`. | Throughput without bypassing any per-record rule. |
| M2.18 | **Imports:** .xlsx is converted to CSV at upload (first sheet, values only, unpacked-size guard). Targets are module schema keys (legacy `company_name` and `custom.<key>` still accepted) and exclude hidden and read-only fields. Dedupe: create (default) / skip / update, matching contacts by email then phone, companies by website then name, products by SKU then name, deals by name within the pipeline. "Check file" is a full dry run. A create refused by the plan limit **stops** the import at that row (`status=stopped`; `stop.upgrade` names the edition or add-on); earlier rows stay. **Rollback** deletes created records only if unchanged since the import and not in use (notes, files, linked records), restores updated records only if unchanged, and reports everything else as a conflict; it releases record slots and is audited per record (`imports.rolled_back`). Migration presets (Zoho CRM, HubSpot, Pipedrive) are header-mapping presets only. The 10,000-row / 5 MB per-file limit is unchanged. | Rollback must never overwrite someone else's work or leave dangling references. |
| M2.19 | **Exports:** columns now come from the module schema (more columns than before; the leading columns keep their order). "Full export" (`/exports/all/`) is a ZIP with one CSV per module the member may export, hierarchy and field rules applied, 100,000 rows per module. | One source for columns; the production shape kept where it matters. |
| M2.20 | **Timeline** is a named source registry with time-cursor paging (`before` / `next_before`); `sources` lists what a record's timeline is made of. Files are a source; M4 and M6 channels register new sources. Field-change rows no longer name hidden fields. Without `limit` the endpoint still returns up to 200 events (older clients). | Pluggable, no fixed union query. |
| M2.21 | **Kanban:** first load up to 200 cards per column (`per_stage`, max 500), the rest paged per column (`/deals/board/stage/`); columns are windowed in the browser. Counts, value totals and the weighted forecast are computed on the server over every deal in scope. Cards can be edited inline (name, amount, close date) and show the pipeline's layout fields. Measured: a 1,000-deal board in 169 ms server time. | Under one second end to end with room to spare. |
| M2.22 | **Stage-transition hook:** `apps.pipelines.transitions.validate()` runs in `move_stage` (Kanban drag, stage dialog, Sheet, imports) before anything is written; M2 registers a pass-through validator. A refusing validator raises `TransitionRefused` (409 `stage_transition_refused`). | M5 supplies rules without touching the stage-change path. |
| M2.23 | **Connected pipelines:** `DealConnection` links any two deals (usually across pipelines), at most 20 per deal, shown on both; the other deal is listed only if the member may view it. `deals.services.create_connected_deal()` is the M5 hook ("on stage X, create a deal in pipeline Y"); no configuration UI in M2. | The automation is M5; the data model and display are not. |
| M2.24 | **Domain events:** `RecordChanged` gains `related` ((entity, id) pairs) and the changes `completed`, `deleted`, `linked`, `unlinked`, `rolled_back`; notes, files and activities publish too. Configuration changes (pipelines, access, price books, saved views) are audited but not published. | Workflows react to records; configuration has its own audit trail. |
| M2.25 | **Fixed (pre-existing):** the RAG subscriber queued re-index jobs for contacts and companies, which are not knowledge sources, so every such edit logged a failed index job; only sources are queued now. A lifecycle-stage change skipped field rules; it now honours `read_only`. | Found while load-testing Sheet edits. |
| M2.26 | **External Record Sharing** moves to **Milestone 6**, with the other public-facing surfaces (forms, booking pages, payment links). | Same threat model: unauthenticated access to tenant data. |
| M2.27 | **Load results** (local PostgreSQL 16, Windows laptop), 1,000,000 contacts: first Sheet window 557 ms, middle 1,187 ms, last 1,139 ms, 200-row edit 2.5 s (`M2_LOAD=1 pytest tests/scaling/test_m2_load.py`). | Recorded for the acceptance criteria; deep windows are bounded by the exact count at 1M rows. |
